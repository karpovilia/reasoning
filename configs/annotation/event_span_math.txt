You are an expert annotator of LLM reasoning traces. You label *cognitive events* by their MEANING, not by surface keywords. The trace is split into numbered segments. Identify every occurrence of these event types (and ONLY these):

- backtrack — the model cancels/revises a step or conclusion it just made and goes back: changes direction, catches its own error, rethinks. The essence is a REVERSAL of the reasoning flow. (Markers like "wait", "actually" are only sometimes present; backtrack without them still counts.)
- verify — the model checks the correctness of an ALREADY obtained step/result: recomputation, substituting back, sanity-check, checking a sign/bound/condition. Not the first computation, but its check.
- branch — the model explicitly considers several alternatives/cases: case 1/2, "alternatively", "either ... or", enumerating options, a separate branch.
- subgoal_done — an intermediate result of a subtask is fixed: a quantity/figure/lemma is derived, a stage is finished ("so the circle is ...", "therefore X = ..."). Not the final answer.
- failed_attempt — the model admits an approach/hypothesis does NOT work: dead end, contradiction, "this doesn't work", abandoning a branch.
- commit — the model fixes the FINAL answer to the problem.

Crucially, an event counts even when there is NO lexical marker — judge from what the model is actually doing.

Output exactly ONE JSON object, no prose outside it:
{
  "question_id": "string",
  "events": [
    {
      "seg_id": 0,
      "type": "<one of the event types>",
      "trigger_quote": "exact substring of segment seg_id",
      "onset": "start|mid",
      "confidence": "high|medium|low",
      "rationale": "1 short phrase: why this is an event of this type"
    }
  ],
  "trace_summary": "1-2 sentences: how the model solved overall"
}
Rules:
- "trigger_quote" MUST be copied verbatim from the segment it points to.
- "onset" = "start" if the event fires from the beginning of the segment, "mid" if inside
  (then trigger_quote localizes the spot).
- Do NOT force an event onto every segment: smooth uninterrupted derivation contains no
  events. Prefer missing a doubtful case over stamping a false positive.
- One segment MAY carry several events (e.g. subgoal_done + verify) — then several
  records with the same seg_id.

Operator vocabulary for spans (MECE — every segment belongs to exactly one):
- SETUP — restating the problem, planning, decomposing into subtasks, setting notation.
- DERIVING — smooth forward derivation/computation along one path (the uninterrupted stretch that typically contains no events).
- EXPLORING — considering alternatives/cases/branches: enumerating options, working a separate case.
- VERIFYING — a sustained stretch of checking/recomputing already-obtained results (substituting back, sanity checks).
- REVISING — recovery after a dead end or reversal: the model is undoing and redoing work, changing course.
- CONCLUDING — finalizing: assembling and fixing the final answer.

Additionally, produce "spans": an EXHAUSTIVE contiguous partition of the labeled segment
range into operator spans (modes/phases):
  "spans": [
    {"span_id": 0, "seg_start": <int>, "seg_end": <int>, "operator": "<one operator>",
     "rationale": "1 short phrase (may name the boundary-triggering event)"}
  ]
Span rules:
- Half-open intervals [seg_start, seg_end); spans sorted; the first span starts at the
  FIRST labeled segment; each next seg_start equals the previous seg_end; the last
  seg_end is one past the LAST labeled segment. No gaps, no overlaps.
- Every labeled segment falls in exactly one span. Do NOT invent an "other" operator.
- Spans are modes lasting one or more segments; do not emit a new span for every
  segment — switch spans only when the mode actually changes.
- Events and spans are coupled but distinct layers: a branch event usually OPENS an
  EXPLORING span; subgoal_done often CLOSES a DERIVING span; backtrack/failed_attempt
  usually STARTS a REVISING span; commit lies INSIDE a CONCLUDING span. A brief verify
  in the middle of a derivation does NOT open a VERIFYING span — only a sustained
  checking stretch does. Span boundaries often coincide with events but need not.
The output JSON object must contain BOTH "events" (as specified above) and "spans".
