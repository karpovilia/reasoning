# Пилот собственного шума судьи-разметчика: полные результаты

Дата: 2026-08-15. Контекст, зачем эксперимент нужен и как устроен полный дизайн —
docs/findings/2026_08_15_judge_noise_experiment_RU.md. Здесь
только числа пилота и выводы из них. Судья-разметчик — языковая модель, которая читает
трассу рассуждения и расставляет в ней события шести типов и операторные спаны;
собственный шум судьи — расхождение между повторными разметками одного и того же
текста одним и тем же судьёй при одинаковом входе.

## Что именно прогонялось

Две трассы, по пять независимых проходов судьи на каждую. Вход всех пяти проходов
побайтово одинаков: тот же файл сегментации, тот же системный промпт, те же окна
чанков. Единственный источник различий — стохастика судьи при штатной температуре 0.6.

Трасса первая, gpt-oss-20b, вопрос math500 test/intermediate_algebra/102.json, 28
сегментов, 842 токена, базовое плечо без форс-стопа при лимите 8192. Payload взят
побайтово из
internal_signals_poc/native_po_2026_08_11/judge_payloads/gptoss20/test_intermediate_algebra_102_json.json.
Длина выбрана ближайшей к средней длине плеча 28.3 сегмента при медиане 17: на трассе
медианной длины пять-шесть событий дают слишком грубую сетку значений F1.

Трасса вторая, Qwen3.6-35B-A3B-FP8, вопрос math500 test/intermediate_algebra/860.json,
89 сегментов, 1833 токена, средний уровень усилия, зерно повтора 101. Payload взят
побайтово из
internal_signals_poc/effort_repeats_2026_08_14/judge_payloads/qwen36_35b/medium/seed101/test_intermediate_algebra_860_json.json,
89 сегментов — это медиана уровня medium по трассам без GPQA при средней 90.6. Вопросы
GPQA не брались по лицензионному правилу, обе трассы из math500.

Судья: запрошено имя deepseek-reasoner, фактическая модель из ответа API
deepseek-v4-flash с включённым размышлением, температура 0.6, окно разметки 30
сегментов, контекст 15, потолок вывода 32000 токенов, транспорт через корпоративный
прокси со streaming. Системный промпт собран из qwen_judge.SYS_M, qwen_dual_label.OP_DEFS_M
и SPAN_RULES, хэш sha256
0edee8cd13f652c1b0f826fe8dbe7d3dead21af5f2a03d591544ed94783fdc5f. Блока открытого
словаря заданий 07 и 14 в промпте нет; дописывание этого блока к промпту пилота даёт
ровно хэш c489fc0522f5dc7571f83a26b3b56c984b9783c606afb9d454cc5d2ed1d923ff, то есть хэш
штатной разметки, чем и проверено побайтовое совпадение общей части.

Прогон 2026-08-15 с 11:32 по 11:39 МСК, десять проходов, двадцать вызовов API, ни
одного отказа и ни одного деления окна. Расход 0.06 доллара при остатке счёта 39.58 до
и 39.52 после. Свод посчитан на боксе 192.168.2.48, прогон ученика судьи — на боксе
192.168.2.43, где стоит окружение обучавшего его эксперимента.

## Попарное согласие пяти проходов

Пять проходов дают десять пар. Микро-F1 события считается при совпадении по паре номер
сегмента и тип события, кратности учитываются пересечением мультимножеств. Согласие
операторов спанов считается посегментно: спаны образуют разбиение трассы без дыр и
нахлёстов, поэтому каждому сегменту отвечает ровно один оператор.

| величина | трасса gpt-oss-20b | трасса Qwen3.6-35B-A3B |
|---|---|---|
| микро-F1 событий, среднее по 10 парам | 0.607 | 0.547 |
| микро-F1 событий, разброс по парам | 0.400-0.833 | 0.436-0.759 |
| микро-F1 событий, отклонение | 0.146 | 0.098 |
| макро-F1 событий, среднее | 0.607 | 0.480 |
| операторы спанов, доля согласных сегментов | 0.950 | 0.803 |
| операторы спанов, каппа Коэна попарно | 0.912 | 0.713 |
| каппа Флейса, событие любого типа на сегменте | 0.541 | 0.565 |
| каппа Флейса, оператор спана | 0.912 | 0.712 |

Шум выше у трассы Qwen3.6-35B-A3B. По событиям разрыв невелик, 0.547 против 0.607, а
по операторным спанам он крупный: 0.803 против 0.950 по доле согласных сегментов и
0.712 против 0.912 по каппе. То есть на длинной трассе судья почти так же уверенно
находит, ЧТО происходит в отдельном предложении, но заметно хуже воспроизводит, В
КАКОМ режиме рассуждения это предложение находится.

Каппа Флейса по событию любого типа на сегменте почти одинакова у двух трасс, 0.541 и
0.565. Это важная оговорка: разрыв сырых F1 частично объясняется разной базовой
частотой событий, а не разной надёжностью судьи. Каппа поправляет на случайное
согласие при данной частоте, и после поправки на уровне «есть ли здесь событие вообще»
две трассы неразличимы. Различие живёт в двух других местах: в выборе типа события и в
разметке операторных спанов.

Полученные числа согласуются с прежней грубой оценкой. Побочное измерение задания 13
давало микро-F1 0.729-0.878 по событиям на общем отрезке двух проходов; там правый
контекст помогал согласию, поэтому оценка была верхней. Чистый пилот при полностью
одинаковом входе даёт 0.547-0.607, то есть собственный шум судьи ещё крупнее, чем
считалось.

## Воспроизводимость счётчиков

Счётчики событий на трассу — рабочая метрика проекта, поэтому их разброс важнее
разброса локализации. Коэффициент вариации ниже — это отклонение пяти значений,
делённое на их среднее.

| величина | gpt-oss-20b | Qwen3.6-35B-A3B |
|---|---|---|
| всего событий по проходам | 5, 5, 5, 5, 7 | 27, 24, 32, 31, 31 |
| коэффициент вариации общего счёта | 0.166 | 0.117 |
| размах общего счёта | 2 | 8 |
| число спанов по проходам | 5, 5, 5, 5, 5 | 13, 13, 11, 14, 13 |
| коэффициент вариации числа спанов | 0.000 | 0.086 |

Счётчики по типам на трассе Qwen3.6-35B-A3B: verify 10, 9, 6, 7, 13 при коэффициенте
вариации 0.304; branch 6, 3, 10, 11, 6 при 0.454; subgoal_done 9, 8, 9, 7, 9 при 0.106;
commit 2, 3, 3, 2, 3 при 0.211; failed_attempt 0, 0, 4, 4, 0 при 1.369; backtrack 0, 1,
0, 0, 0 при 2.236. На трассе gpt-oss-20b счётчики почти не гуляют: verify 2, 2, 2, 2, 3;
subgoal_done 2, 2, 2, 2, 3; commit ровно 1 во всех пяти проходах; остальные типы нули.

Сопоставление с разбросом самой генерации из задания 14 полезно для масштаба. Там
медиана коэффициента вариации длины по трём повторам одного вопроса при
зафиксированном уровне усилия составила 0.278-0.347. Шум судьи по общему счёту событий
меньше, 0.117-0.166, но по отдельным типам он этот разброс перекрывает: verify 0.304 и
branch 0.454 сравнимы с разбросом самой генерации, а failed_attempt и backtrack на
порядок хуже.

Число спанов устойчиво: на короткой трассе оно совпадает во всех пяти проходах, на
длинной гуляет от 11 до 14 при коэффициенте вариации 0.086. То есть крупная структура
рассуждения воспроизводится, а её границы — нет, что и видно по согласию операторов
0.803.

## Консенсус-профиль

Каждая пара номер сегмента и тип события получает степень поддержки — сколько проходов
из пяти её поставили. Ниже распределение всех таких пар.

| поддержка | gpt-oss-20b, штук | доля | Qwen3.6-35B-A3B, штук | доля |
|---|---|---|---|---|
| 5 из 5 | 1 | 0.100 | 7 | 0.119 |
| 4 из 5 | 3 | 0.300 | 8 | 0.136 |
| 3 из 5 | 1 | 0.100 | 7 | 0.119 |
| 2 из 5 | 2 | 0.200 | 20 | 0.339 |
| 1 из 5 | 3 | 0.300 | 17 | 0.288 |
| всего меток-кандидатов | 10 | | 59 | |
| средняя поддержка | 2.700 | | 2.458 | |

Главное число этого раздела: полного согласия достигает лишь примерно одна метка из
восьми, 0.100 и 0.119 на двух трассах, а почти треть меток, 0.300 и 0.288, ставит
ровно один проход из пяти. Одиночная разметка одной трассы, то есть штатный режим всех
прошлых прогонов, примерно на треть состоит из меток, которые не переживают
перезапуска.

По типам на трассе Qwen3.6-35B-A3B консенсус распределён очень неровно. У commit из
четырёх меток четверть держится всеми пятью проходами и ни одной одиночной. У branch
из тринадцати меток 0.154 полного согласия при 0.077 одиночных. У subgoal_done из
шестнадцати меток 0.125 полного согласия при 0.313 одиночных. У verify из двадцати
одной метки лишь 0.095 полного согласия при 0.476 одиночных: почти половина проверок,
которые видит судья, видна ровно одному проходу. У failed_attempt все четыре метки
имеют поддержку два из пяти — они пришли целым блоком от двух проходов, а три прохода
не увидели ни одной. У backtrack единственная метка одиночная.

## Примеры: где судья согласен и где спорит

Цитаты приведены дословно из трасс math500, лицензионного ограничения на них нет.

Полное согласие пяти проходов. Трасса gpt-oss-20b, сегмент 21: «Check: starting n=1:
term = F_2/(F_1 F_3) = 1/(1*2)=1/2. n=2: F_3/(F_2 F_4)=2/(1*3)=2/3.» — все пять
проходов ставят verify и все пять относят сегмент к спану VERIFYING. Трасса
Qwen3.6-35B-A3B, сегмент 54: «Conclusion: It is an ellipse.» — все пять ставят commit
и спан CONCLUDING. Там же сегмент 28: «4. Consider alternative interpretation:» — все
пять ставят branch и спан EXPLORING. Там же сегмент 55: «Let's re-read the equation
carefully.» — все пять ставят verify. Общий признак консенсусных мест: в предложении
есть явный речевой маркер намерения, слово «Check», «Conclusion», «Consider
alternative», «re-read».

Спор о наличии события. Трасса gpt-oss-20b, сегмент 13: «So partial sum S_N = 1/F_1 +
1/F_2 - 1/F_{N+1} - 1/F_{N+2}.» — subgoal_done ставят проходы 2, 3 и 5, проходы 1 и 4
не ставят ничего. Там же сегмент 11: «Sum = (1/F_1 + 1/F_2) - (1/F_{N+1} +
1/F_{N+2}).» — subgoal_done ставят проходы 1 и 4, остальные молчат. Это одна и та же
цепочка выкладок: судья согласен, что промежуточный результат где-то здесь получен, но
не воспроизводит, на каком именно шаге это случилось. Трасса Qwen3.6-35B-A3B, сегмент
19: «$\frac{(x - 6)^2}{40} + \frac{y^2}{10} = 1$» — subgoal_done ставят проходы 1, 2 и
3, а проходы 4 и 5 переносят ту же метку на следующий сегмент 20 «This matches the
standard form of an ellipse». Смещение на один сегмент — типичная форма расхождения.

Спор о типе события. Трасса Qwen3.6-35B-A3B, сегмент 22: «Since $a^2 \neq b^2$ ($40
\neq 10$), it is an ellipse, not a circle.» — проход 1 ставит subgoal_done, проход 2
ставит backtrack, проход 3 ставит verify, проход 4 не ставит ничего, проход 5 ставит
subgoal_done. Один и тот же текст прочитан как достижение подцели, как возврат назад и
как проверка. Трасса gpt-oss-20b, сегмент 19: «So limit S = 2 - 0 - 0 = 2.» — проход 4
ставит commit и открывает спан CONCLUDING, проход 5 ставит subgoal_done и остаётся в
DERIVING, остальные не ставят ничего. Здесь расхождение метки тянет за собой
расхождение структуры: момент перехода к финальному ответу сдвигается на несколько
сегментов.

Спор об операторе спана без спора о событии. Трасса Qwen3.6-35B-A3B, сегмент 27:
«Therefore, it is an ellipse.» — commit ставят проходы 2, 3 и 5, при этом проходы 2 и 5
относят сегмент к CONCLUDING, а проходы 1, 3 и 4 — к VERIFYING. Модель уже сказала
ответ, но продолжает проверку, и судья каждый раз заново решает, считать это концом
вывода или частью проверки.

## Шум по типам событий

Сводная таблица. Попарный F1 — среднее по тем парам проходов, где тип встретился хотя
бы у одной стороны. Последний столбец — согласие двух режимов судьи из задания 07,
чат-режим против режима с размышлением на 725 трассах, приведённое для сопоставления.

| тип | F1 на gpt-oss | F1 на Qwen | каппа Флейса на Qwen | коэффициент вариации счёта на Qwen | F1 двух режимов, задание 07 |
|---|---|---|---|---|---|
| commit | 0.600 | 0.653 | 0.643 | 0.211 | 0.581 |
| subgoal_done | 0.450 | 0.595 | 0.553 | 0.106 | 0.519 |
| branch | нет меток | 0.558 | 0.547 | 0.454 | 0.360 |
| verify | 0.770 | 0.494 | 0.456 | 0.304 | 0.440 |
| failed_attempt | нет меток | 0.143 | 0.236 | 1.369 | 0.253 |
| backtrack | нет меток | 0.000 | -0.002 | 2.236 | 0.474 |

Твёрдые типы — commit и subgoal_done: у них самый высокий попарный F1 и самая высокая
каппа на длинной трассе, а у commit ещё и самый высокий уровень полного согласия. Это
согласуется с их природой: фиксация ответа и получение промежуточного результата
привязаны к формуле или к явной фразе вывода.

Жидкие типы — failed_attempt и backtrack. Каппа Флейса у backtrack равна нулю в
пределах округления, то есть согласие проходов по возврату назад неотличимо от
случайного при его редкости. У failed_attempt все метки пришли от двух проходов из
пяти и полностью отсутствуют у трёх — тип срабатывает не пометками, а пачками, что
похоже на разовое решение судьи «здесь модель признаёт тупик», принимаемое на уровне
всего чанка.

Отдельно verify. На короткой трассе gpt-oss он самый твёрдый тип, F1 0.770 и каппа
0.753, потому что проверок там ровно две и обе помечены словом Check. На длинной трассе
Qwen он один из самых жидких, F1 0.494, каппа 0.456, коэффициент вариации счёта 0.304,
и почти половина его меток одиночные. Это прямо связывает пилот с находкой задания 07:
там режим с размышлением добавлял к чат-режиму 2671 проверку против 1201 совпавшей, то
есть verify был главным типом расхождения двух режимов. Пилот показывает, что заметная
доля этого расхождения — не свойство режима, а собственная невоспроизводимость судьи на
длинных трассах с протяжными самопроверками.

Порядок типов по стабильности в пилоте и порядок по согласию двух режимов из задания 07
совпадают почти полностью: commit и subgoal_done наверху, failed_attempt внизу. Исключение
одно — backtrack, у которого межрежимный F1 0.474, а внутрирежимная каппа около нуля;
объяснение простое — на одной трассе он встретился один раз, и оценка по одной метке
ничего не значит.

## Насколько разметка с открытым словарём отличается от разметки без него

У обоих payload есть штатная разметка, сделанная заданиями 07 и 14 тем же судьёй, но с
дописанным блоком открытого словаря. Согласие этой штатной разметки с пятью пилотными
проходами: на трассе gpt-oss-20b микро-F1 0.730 при разбросе 0.545-0.923 и согласие
операторов 0.971; на трассе Qwen3.6-35B-A3B микро-F1 0.608 при разбросе 0.480-0.737 и
согласие операторов 0.654.

Числа не ниже, а на событиях даже выше, чем согласие пилотных проходов между собой,
0.607 и 0.547. Значит, дополнение промпта про открытый словарь не сдвигает канонические
слои за пределы собственного шума судьи — требование инструкции задания 07 размечать
канонические слои так, как будто дополнения нет, выполняется на этих двух трассах.

## Ученик судьи против консенсуса

Проверялось, учится ли обученный детектор именно на устойчивой части разметки. Ученик —
лёгкий теггер сегментов эксперимента sft_judge_distill_2026_08_13, чекпоинт
internal_signals_poc/sft_judge_distill_2026_08_13/outputs/light2/light_pooled.pt:
замороженные эмбеддинги предложений кодировщиком sentence-transformers/all-MiniLM-L6-v2,
тринадцать вспомогательных признаков, вектор модели-источника, двунаправленный
рекуррентный слой и шесть независимых вероятностей на сегмент. Прогон на боксе
192.168.2.43 скриптом
internal_signals_poc/judge_noise_pilot_2026_08_15/src/detector_on_consensus.py,
сборка признаков и класс модели импортированы из train_light.py того же эксперимента, чтобы вход
совпадал с обучающим.

| величина | gpt-oss-20b | Qwen3.6-35B-A3B |
|---|---|---|
| средний скор на метках 4-5 из 5 | 0.182 при 4 метках | 0.090 при 15 метках |
| средний скор на метках 1-2 из 5 | 0.187 при 5 метках | 0.057 при 37 метках |
| средний скор на клетках без единого голоса | 0.045 при 158 клетках | 0.022 при 475 клетках |
| ранговая связь поддержки и скора | 0.056 | 0.087 |
| средний перцентиль скора при поддержке 5 из 5 | 0.988 | 0.822 |
| средний перцентиль скора при поддержке 1 из 5 | 0.835 | 0.786 |

Вывод двойственный. Ученик уверенно отделяет размеченные судьёй клетки от фона: средний
скор на любой судейской метке выше фонового в три-четыре раза, а средний перцентиль
скора в каждой группе поддержки лежит выше 0.72, то есть детектор смотрит примерно
туда же, куда судья. Но
внутри разметки он консенсус почти не выделяет: на трассе Qwen скор на консенсусных
метках выше слабых в 1.6 раза, на трассе gpt-oss разницы нет вовсе, а ранговая связь

33.14. Для масштаба: все десять проходов flash по двум трассам стоили 0.06 доллара.
Проход pro занимает 421-504 секунды против 224-368 у flash. Отказов и делений окна нет
ни одного, все девять вызовов API завершились штатно.

Возможное продолжение: те же три прохода pro на короткой
трассе gpt-oss-20b, где внутренняя база flash 0.607, — это стоит около 0.03 доллара и
показывает, держится ли прибавка pro на трассе другой длины и другой модели.
